# 什么时候需要写适配器

接入前先列清两个问题。引擎能返回哪些请求、标识、计数、阶段和终止记录？模型的选定层究竟计算什么，权重位于哪里？两者分别决定引擎和模型适配器的工作量。

## 引擎

1. 用原生服务的公开接口取得模型列表，核对指定 alias、checkpoint 实际路径、监听端口对应的本地进程、可执行文件及设备。把版本、启动参数和文件内容身份收进 resolved target。
2. 实现请求构造和响应解码。保留线上发送的 JSON 字节、HTTP 状态、分块实体内容及单调时钟。完成 vLLM 的请求 ID、终包、usage 和回显 ID 检查；llama.cpp 的原生结束标志与计数按该版本源码处理。
3. 给原生阶段写清起止边界。聚合差分要有独立空闲窗口、唯一 model/engine 标签、成功数和生成计数证据。不能隔离时保留客户端记录，严格阶段试验报告失败。
4. 在能力表中登记 supported、conditional 或 unsupported，实际执行后再以原件给出 verified。单独记录私有实例关闭、请求取消、队列变空和健康检查。
5. 加入协议试跑、异常分片/计数/身份拒错和真实 CUDA 执行记录，再用受控 suite 验证。启动原生服务沿用独立进程组、明确端口和固定内存、温度保护线。

## 模型

基础请求只依赖模型与部署身份。深度路径还需要层的数学定义、布局、dtype、权重和 scale 的解释。已验收的 Qwen 混合量化与标准 BF16 两条诊断各有自己的公式与参考。

标准 dense 路径检查两个真实 prompt token 在首层 RMSNorm 和 down projection 的完整输出行。从实际 checkpoint 取得 epsilon、维度、是否有 bias 与权重内容，按 FP64 参考独立核对。诊断请求保存所选输入输出和可复算片段，正式请求单独采集。融合残差、不同 norm 缩放或新量化需要独立定义边界与容差，再用真实请求验证。
